Building an Agentic Dispute Resolution System: Multi-Agent LLM Pipeline with RAG, Interpretable ML, and Governance

Credit card disputes are an $83B+ annual problem in the US,[1] and most resolution is still manual: analysts read statements, check records across fragmented databases, look up the applicable clause in a rulebook, and make a judgment call. Automation exists at the edges, but the core reasoning step remains largely human-driven.

This project automates that pipeline with a three-agent system that combines traditional ML with agentic tools orchestrated by LangGraph, grounded in the actual Visa Core Rules.[2] The goal was not just to get something running but to make deliberate engineering decisions that hold up to scrutiny: interpretable classifiers over black-box models, deterministic policy guards over pure LLM judgment, and a full audit trail for every decision made.

RAG Evaluation

Getting the Visa rulebook retrieval right

The Investigator retrieves the specific Visa Core Rules[2] clause that applies to each dispute's reason code and surfaces it verbatim with section number, page, and relevance score. Getting there required four iterations on chunking strategy, evaluated against a golden set of 50 test queries drawn from the rulebook.

The core problem with flat chunking was that section headings were being split away from their content. Some rules were spread across multiple pages, making them nearly impossible to retrieve as a coherent unit without something more structured. A chunk about the 120-day filing limit had no indication it belonged to clause 11.7.5.4. The fix was prefixing every chunk with its full ancestor breadcrumb:[3]

[Dispute Resolution > Dispute Category 10 > Dispute Condition 10.4 > Dispute Time Limit]

This gave embeddings enough structural signal to rank by section, not just keyword similarity.

Hit@3 = fraction of 50 test queries where the correct Visa clause appeared in top-3 results. MRR = mean reciprocal rank of the first correct result.

The key learning here was that RAG over dense regulatory documents is fundamentally a structure problem, not a similarity problem. Once the chunks carried their structural lineage, retrieval quality improved dramatically and plateaued. Chunking strategy matters far more than embedding model choice when the source document has deep, explicit hierarchy.

Interpretable Classifier

Why a Decision Tree over XGBoost

The Investigator runs a Decision Tree as one of its five tools. The choice was deliberate: a Decision Tree produces an extractable decision path that is human interpretable and can be traced back, unlike a black-box model that returns only a score.

When the agent calls the classifier, it gets back not just a fraud probability but a full decision path showing exactly which feature thresholds were crossed and in what order. Click the replay button to watch the path unfold:

A reviewer or regulator can follow exactly what the model saw and challenge any step. This is how compliance teams actually document model-assisted decisions, not as an opaque score but as a traceable path.

The model was trained on 5,000 rows of IEEE-CIS[4] calibrated dataset. The IEEE-CIS dataset was not used directly as training data: its column names are anonymized (V1 through V339) and the feature semantics are not disclosed, making it unsuitable for a domain-grounded classifier. Instead, its statistical distributions, fraud rates, and velocity patterns were used to parameterize a dataset with interpretable, domain-meaningful features.

Token cost and inference efficiency

Running a Decision Tree for fraud scoring adds meaningful signal to the Investigator without adding LLM tokens. Offloading the fraud probability to a local model keeps the Investigator prompt focused on synthesis rather than raw feature reasoning, which reduces both cost and output length. The deterministic pre-checks in the Auditor serve the same purpose: four of six policy rules run in Python before any LLM call, saving tokens for the two checks that genuinely require language reasoning.

Governance

Full audit trail and replay

In a production financial system, a decision that cannot be explained after the fact is a liability. Every pipeline run writes a complete audit record to both an append-only log and a queryable SQL database, covering the full DT decision path, all RAG chunks with relevance scores, all tool call results, the LLM reasoning trace, and all six policy check outcomes.

A separate replay dashboard lets any reviewer pull up a past run by ID and step through exactly what every agent saw and decided. This allows a reviewer to audit all decisions even years later, without re-running the pipeline.

Pipeline verdict accuracy across 50 hand-crafted scenarios is under 70%. The system is conservative by design: the 0.85 confidence floor pushes the Investigator toward escalation on ambiguous cases rather than risking a wrong approve or reject. The scenario categories where accuracy is perfect (duplicate disputes, policy violations, reason code mismatches, legitimate charges) are precisely the ones a compliance tool needs to get right. Over-escalation to a human reviewer is a tunable parameter; a missed fraud or an incorrectly approved policy violation is not.

Future work

What I would do next

1
Train on real dispute outcomes. The classifier uses dataset calibrated to IEEE-CIS distributions because the actual dataset has anonymized feature names (V1 through V339) with no disclosed semantics, making it unsuitable for a domain-grounded fraud tool. As the system processes real disputes, those audited outcomes become far more valuable training signal and a retraining pipeline would make the classifier progressively sharper on the actual distribution it encounters in production.
2
Add a fairness evaluation slice. The current eval measures accuracy and retrieval quality but not disparate impact. A production system should be stratified by merchant category, geography, and dispute amount to check whether verdict distributions differ across groups in ways not explained by fraud signal strength. This is a prerequisite for responsible deployment.
